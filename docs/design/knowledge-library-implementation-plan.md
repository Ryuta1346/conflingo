## 目的と初版の範囲

会議で使った資料をこのMacに明示保存し、アプリ再起動後も次の会議で選択して使えるようにする。

| 操作 | 初版の振る舞い |
|---|---|
| 保存 | Meeting準備画面で取り込み済みのMarkdown/Textを1文書単位、リポジトリを取り込み済みファイルのまとまり単位で保存 |
| 一覧 | 共通ナビに「資料ライブラリ」を追加。名前・種別・文書数・保存更新日時を表示し、新しい順に並べる |
| 検索・閲覧 | 保存名の部分一致検索（日英・英字大小を区別しない）、保存時の文書一覧と本文を読み取り専用で確認 |
| 再利用 | Meeting準備画面の「ライブラリから追加」で1件ずつ明示選択。元ファイルがなくても保存本文を読み込む |
| 更新 | 準備画面で取り込み直した資料から「既存の保存資料を更新」を選び、対象名と更新内容を確認して置換。同じ種別のみ |
| 削除 | 対象名を示す確認後、ライブラリ内の保存だけ削除 |

一覧からの直接ファイル取り込みは追加せず、既存のMeeting取り込み経路を使う。ライブラリ全体の本文検索は初版対象外であり、名前検索と表示する。会議へ追加後は既存の本文検索、手動質問、自動提案、終了後要約で参照できる。

PDF/OCR、クラウド同期、ファイル監視による自動更新、自動保存、資料編集、保存会議のAI再生成は含めない。既存Sessionsの保存形式は変更しない。

## 保存と再利用の契約

1. ライブラリ項目はUUID・形式版・種別・表示名・保存作成/更新日時・改訂IDと、文書本文・元の取り込み日時・出典情報を持つ。Markdown/Textは正規化後の本文を保存し、行位置が再利用前後で変わらないようにする。
2. リポジトリは実際に会議へ取り込まれているファイルだけ保存する。取り外し済みファイルは含めない。相対パス・内容ハッシュ・取り込み時点のsnapshot IDを保持し、文書一覧で保存対象を確認できる。元リポジトリ全体を保存したと表示しない。
3. 絶対パス、security-scoped bookmark、APIキー、送信許可、音声、会議の発話・AI出力はライブラリ項目へ保存しない。ただし選択された本文中の秘密情報を自動除去する機能ではない。保存前に「選んだ資料の本文をこのMacに保持する」と明示する。
4. 明示保存前は会議内だけで保持し、会議破棄・アプリ終了で失われる。保存後はライブラリから削除するまで残る。会議破棄とライブラリ削除は別操作。
5. ライブラリから会議へ追加すると、その時点の保存版を会議へコピーする。元の取り込み日時と出典を維持し、会議へ追加した日時を原本の更新日時として扱わない。保存名と改訂を会議内の資料表示へ関連付ける。
6. 保存項目を更新・削除しても、既に会議へ追加された本文・検索結果の根拠・完成した引用・Sessionsの引用抜粋は変えない。会議側の取り外しもライブラリには波及させない。
7. 最新版を会議へ反映するには、準備中に旧版を取り外して追加し直す。同じ保存項目が既に会議内にある場合は重複追加を抑止し、この操作を案内する。内容が同一の通常文書は既存の本文重複判定も適用する。
8. 保存の二重クリックで項目を重複作成しない。同じ会議内資料の再保存は保存先IDを維持し、同一内容は保存済みとして扱う。別の取り込みを既存項目へ反映する場合は、利用者が更新先を選び確認する。同名だけで自動上書きしない。
9. 更新失敗・削除失敗では既存保存版を保持し、成功とは表示しない。ライブラリ項目の更新履歴を蓄積する機能は追加せず、使用中の会議と保存済み引用が持つ旧版だけ保持する。

## 許可・取消・上限

- 保存、一覧、本文閲覧、会議への追加だけでは外部送信しない。ライブラリはAI送信許可を記録・復元しない。
- 新しい会議では従来どおり送信許可は初期オフ。ライブラリからの追加成功時には、既にオンだった手動・自動提案の資料許可もオフに戻して再確認を促す。AI全体の許可は別管理とし、要約は既存の生成前確認を使用する。
- 手動・自動・要約の送信抜粋上限と、それぞれ独立した許可は維持する。資料変更による生成取消と遅延応答の棄却を既存revision制御へ接続する。
- 追加と保存/更新の起点は準備画面・idleのみ。処理中は重複操作と会議開始/破棄を抑止し、対象のsession ID・操作IDを検証して完了させる。UIの非表示だけで遅延処理を次の会議へ適用しない。
- 保存項目の追加失敗は全体を取り消し、会議の既存資料・索引を保持する。リポジトリを部分的に追加して成功扱いにしない。
- 会議の上限は通常文書20件、1文書1 MiB・10万文字、通常文書合計50万文字。リポジトリは1つ、最大1,000ファイル・500万文字・20 MiBで既存の各ファイル上限も維持する。保存経由でも迂回できないようにする。
- ライブラリ初版は最大100項目、JSONファイル合計200 MiB、1項目64 MiBを上限とする。これは保存形式の上限であり、取り込み本文の上限を緩めない。上限超過では追加・更新を拒否し、既存項目を自動削除しない。破損した管理対象ファイルも容量に数える。

## 保存実装と画面

- `KnowledgeLibrary/`配下に版付きの保存モデル、ファイル保存actor、一覧/選択/詳細の状態とViewを置く。新しい外部依存やネットワーク接続は不要。
- Sandbox内Application Supportの`ConfLingo/KnowledgeLibrary`にUUID名の1項目1 JSONを保存。検索索引は永続化せず、会議へ追加するときに既存FTSへ再構築する。表示名・相対パスを保存先パスとして使用しない。
- actorでファイル操作を直列化し、原子的な置換を使う。保存成功後に一覧と保存済み表示を更新する。デコード前にファイルサイズを確認し、形式版・ID・種別・時刻・本文量・重複ID/パス・相対パス・ハッシュ・出典の整合を検証する。
- 管理先と対象ファイルのリンクや非通常ファイルを拒否する。破損・未知版の1件が正常な他の項目を妨げないようエラー行を表示する。自動修復・自動削除・未知版への上書きはしない。破損項目の明示削除ではライブラリ内の対象だけを扱う。
- 全本文を一覧の画面状態へ保持しない。一覧処理はUIスレッド外で実行し、詳細は選択した項目だけを読み込む。古い一覧/詳細/保存の結果で新しい選択・更新・削除を上書きしない。
- 共通ナビの「資料ライブラリ」で空状態、名前検索、一覧、本文詳細、削除確認、失敗状態を表示する。Meetingの「ライブラリから追加」は選択画面であり、操作中の会議を置換しない。
- 本文は実行しないプレーンテキストとして表示する。リポジトリ詳細ではファイル一覧から1文書ずつ表示。保存名・日時・元の取り込み日時を区別する。
- 保存/更新先の選択画面では対象・本文保存・更新先を確認できる。削除確認では使用中の会議・保存済み引用・元ファイルが残ることを説明する。アプリ独自の暗号化保管や完全消去とは表示しない。
- 既存DesignTokensを使い、狭幅ナビ、設定文字サイズ、キーボード、VoiceOverラベルを整える。既存の停止確認、フローティングMeeting、Sessions閲覧を回帰対象にする。

| L08 | 保存/追加中のreset、更新/削除と遅延読込、画面遷移、二重操作で古い完了を誤適用しない。fakeの待機点で競合を再現 |
| L09 | 復元資料を手動・自動・終了後要約で参照し、正しい引用を表示/出力。未送信引用の拒否・誤確定防止・取消を回帰 |

| L11 | 100項目の一覧/名前検索、1,000ファイルのリポジトリ追加の所要時間とメモリを記録。全本文の恒常保持やUI停止を確認し、問題があれば修正 |
| L12 | 無通信のネイティブUIで保存→再起動→選択→検索/引用→更新→削除を確認。狭幅・拡大文字・キーボード・VoiceOverを確認し、未確認は明記 |

## 実装順序と検証

1. 承認を記録。`plan.md`と詳細計画の現在地をローカルmainに合わせて修正し、情報設計、保持/破棄説明、日本語/英語README・利用ガイドへ承認済みの予定を反映する。未実装を実装済みとは記載しない。
2. `tdd`スキルの実行契約と専門観点を確認。保存/再読込・失敗保持・更新/削除の利用者向け振る舞いをテストし、意図した失敗を確認してから最小実装する。
3. 保存スナップショットと会議への追加をTDDで実装し、上限・原子性・許可・取消・出典維持を確認。既存の取り込み検証を重複させず共通の契約として利用する。
4. 一覧・詳細・選択・保存/更新・削除のUIとナビを接続。合成データで操作と検索/AI/要約のfake連携を検証する。
5. 全テスト、SwiftLint `--no-cache --strict`、Debug/Releaseビルド、差分チェックを実施。テスト/プレビューは専用保存先を注入し、利用者の既存資料・保存セッション・APIキーを使わない。
6. 不要コード・古い説明を整理し、`docs/validation/knowledge-library.md`へRed/Green、最終検証、UI・性能結果、未検証事項を記録する。独立レビューを行っていない場合も明記する。

これは新機能のローカル実装・検証計画であり、実API送信・実音声収集は不要。既存のGate A/B/C/U/D、Sessionsの残る受入、実モデル品質、配布条件、60分耐久を完了扱いにしない。初版の機能・失敗処理まで一体で完了させ、Gitコミット・push・PR作成・マージは明示依頼時のみ実施する。
