## 現行コードから分かった接続条件

1. `DualTranscriptionController`は開始ごとに非公開の`TranscriptEventHub`を生成し、停止時に破棄する。既存購読は`MeetingSessionStore`用で、その失敗は音声停止へつながる。AI用は任意の独立購読として分離し、AI購読失敗を音声停止へ伝播させない。
2. Hubは過去イベントを再送しない。開始/再開ごとに音声入力より先にAI購読を接続する最小のライフサイクル境界を設ける。履歴が必要な手動要求は既存storeの確定発話からスナップショットを作る。AIのために全文履歴を別storeへ複製しない。
3. `MeetingWorkspace`は主画面と小窓で共有され、`insights`と文字列の`aiStatus`を保持する。AI状態を型で扱い、表示文言をそこから導く。停止・破棄・新会議への遷移とAI取消を同じ所有者で調整する。
4. `MeetingInsight`は生成時にローカルUUIDを作り、種類を文字列で持つ。ストリームの同一カード更新に必要な安定ID、型付き種別、生成状態、根拠不足の区別を追加する。DEBUG fixtureも更新する。
5. `MeetingSessionStore`は会議ID、発話ID/revisionを検証し、final確定後の更新を拒否する。AIもpartialを送信せず、同じfinalを再分析しない。根拠は当該リクエストに含めた発話IDと照合する。

## 操作・データ契約案

### 送信許可と停止

- 音声取得への通知・同意確認とAI送信許可を分ける。送信先、モデル、送信対象、提供者のデータ利用/保持条件を説明できる状態で許可操作を提供する。
- AI許可は会議単位で初期オフ。新会議・送信先変更時は再許可を必要とする。許可前の発話を自動で遡及送信しない。手動Ask AIで既存発話を含める場合は、その送信範囲を操作前に説明する。
- 送信するのは質問文、必要な確定発話、入力元、言語、時刻、匿名の参照IDに限定する。音声PCM、会議名、ファイルパス、資料、他会議の発話は含めない。
- AIオフ、Pause、End、設定への移動に伴う停止、入力障害、破棄では待機要求を破棄し、通信取消と世代番号の更新を行う。遅延応答は会議ID・要求ID・世代番号で拒否する。停止直前finalは字幕へ取り込むが、新規AI送信は起動しない。
- 小窓の非表示/展開だけではAIを停止しない。Pause/Review中は新規Ask AIを無効とする。再開で待機要求を再送せず、新規操作/発話から再開する。
- 取消は既送信データの撤回や課金取消ではない。HTTP通信を取消し、完了カードは読み返せるまま保持する。中断カードは完了扱いしない。

### 要求の制限と根拠

- 手動要求は1件まで。実行中の自動生成は手動操作時に取消し、手動生成中の自動要求は溜めない。
- 自動提案は会議ごとに初期オフで、外部送信許可とは別スイッチにする。オフの間は検出用も含め自動のLLM呼び出しをしない。オン時は最大2件/分、最短12秒間隔。発話IDとトリガーを使って重複を抑制し、同じ内容の提案も正規化した本文で抑制する。意味の類似判定のための追加LLM呼び出しは行わない。単調時計を注入してテストする。
- 初期上限案は、文脈が直近30確定発話かつ合計12,000文字、質問が2,000文字、HTTP本文が128 KiB、生成は`maxOutputTokens: 1024`かつ受信本文が8,000文字。上限内で新しい発話を優先し、UIには文脈の範囲を示す。巨大な単一発話は部分送信せず除外を表示する。思考レベルは`minimal`を指定する。モデルの出力上限より小さく設定し、`MAX_TOKENS`による打切りや構造化結果の欠落は失敗として扱う。
- リクエスト全体の期限は初期案30秒。自動の通信再試行は行わず、手動再試行で新しい要求IDを発行する。401/403/429/5xx、途中切断、タイムアウトを区別する。
- 根拠IDは送信済み発話の許可集合で検証し、存在しないIDや別会議のIDは採用しない。根拠がない/不正なら引用を捏造せず「要確認」とする。発話時刻・引用文はローカルの元発話から表示する。
- 発話内容は分析対象のデータとして渡し、発話内の指示でシステム設定・送信先・機密情報を変更させない。AIに外部操作ツールを与えない。決定/アクションは全て未確認候補。

### 直接接続と将来の切替

- 共通の`InsightClient`（仮称）は、文脈・質問を受け、生成中/本文更新/完了/失敗のイベントを返す。Provider固有の認証・URL・JSON/SSE変換は`GeminiInsightClient`へ閉じ込める。UIや要求調整にGemini固有DTOを漏らさない。
- 本番の目標は「利用者のAPIキーによる直接接続」と「ConfLingo運営Proxy」の選択式。Providerと接続経路を同一概念にしない。今回はGemini直接接続とモックの実装だけで、この境界から将来アダプタを追加する。未使用のProxy実装やプラグイン機構は作らない。
- `URLSession`によるHTTPS REST＋SSEを計画する。`streamGenerateContent?alt=sse`と`x-goog-api-key`認証は[公式リファレンス](https://ai.google.dev/api)・[テキスト生成](https://ai.google.dev/gemini-api/docs/generate-content/text-generation)に記載。GeminiのSSEを内部イベントへ変換するので、内部の`insight.created`等がGoogleから返るとは想定しない。
- 安定したカードIDと要求IDはアプリ側で付与する。JSON schemaで種別/本文/根拠IDを要求し、受信完了時に検証する。生成中は未検証として表示し、部分JSONを完成カードとして扱わない。根拠ID、正常終端、必須フィールドが揃うまで完了にしない。
- 通信分割やUTF-8分割、空応答、安全性によるブロック、出力上限、不正なJSON、終端欠落を処理する。再接続/再送は自動化せず、同じ要求の二重課金を避ける。
- 設定でキーの登録/置換/削除を行う。保存先はKeychainのみ。保存に失敗した場合にUserDefaults等へフォールバックしない。キーをURL、ログ、fixture、ソース、リポジトリへ書かない。テストは一時的な専用項目を使用し、利用者の既存キーを変更しない。
- 接続先はGoogleの公式HTTPSホストに限定し、任意URLへのキー送信を許さない。リダイレクト時も資格情報を別ホストへ転送しない。キー変更/削除時は通信を取消し、会議のAI許可をリセットする。
- ログへ発話・質問・回答・キーを保存しない。会議ID/要求IDの照合はローカルで行い、送信には必要な参照IDだけを含める。会話本文を含むネットワークキャッシュを残さない構成にする。

### 初期モデル・費用・データ条件（2026-11-08公式資料確認）

- **選定案: `gemini-3.1-flash-lite`。** [料金表](https://ai.google.dev/gemini-api/docs/pricing)のStandard料金は入力$0.25、出力$1.50／100万トークン。`gemini-3.5-flash-lite`は入力$0.30・出力$2.50で、まずコストを優先して3.1を評価する。[3.5の公式紹介](https://ai.google.dev/gemini-api/docs/generate-content/whats-new-gemini-3.6)
- 2.5 Flash-Liteは単価が低いが、[モデル一覧](https://ai.google.dev/gemini-api/docs/models)では過去の利用者にアクセスが制限されるため新規PoCの既定にしない。3.1 Flash-Liteの最早終了日は2027-05-07と[終了予定](https://ai.google.dev/gemini-api/docs/deprecations)に記載。実装開始時に提供状況を再確認し、利用不可の場合は自動で高額モデルへ切り替えない。
- [思考設定](https://ai.google.dev/gemini-api/docs/generate-content/thinking)の`minimal`で費用と遅延を抑える。思考トークン0の保証ではない。検索Grounding、外部ツール、ファイル送信、追加の要約LLMは使わない。
- 概算例: 1回あたり入力3,000・課金対象出力500トークンなら$0.0015、20回で約$0.03。Standard単価からの試算で、実測や月額上限ではない。出力に課金対象の思考も含めて計算する。実際の利用量はAPIが返すusage情報を記録し、未取得なら不明扱いとする。
- 無料枠と有料枠はデータ利用条件が異なる。[Googleの利用条件](https://ai.google.dev/gemini-api/terms)では無料サービスの入出力は製品改善に使われ得る一方、有料サービスは製品改善に使用しないが不正利用検出等で限定的に保持される。PoCの実通信は架空の合成テキストだけとし、キーだけから契約区分やゼロ保持を断定しない。利用者自身の課金設定は変更しない。
- 実会話を使う将来の受入では、利用するプロジェクトの契約区分と送信条件を確認して表示へ反映する。OpenAI/Anthropic等のサブスク連携は希望事項として記録し、公式に提供・許可される方法を別途調査する。利用可能とはまだ判断していない。
