# PR #48 CI失敗の修正計画

2026-11-15。対象 `feat/dr3-design-system`、基点 `375f0cd`。
ユーザー「修正して」により、CI修正後のマージ・main切替・対象ブランチ削除まで承認済み。

## 確認済みの失敗

[run 43698785395](https://github.com/Ryuta1346/conflingo/actions/runs/43698785395) の初回・再実行とも失敗。
再実行では `LiveTranscriptLayoutTests.conferenceManualHistoryScrollIsNotTakenOverByPartialUpdates` がAX要素取得に失敗し、`InsightHTTPTransportTests` の長文・2 MiB境界ケースが60秒を超えた。ローカル全748テストは成功していた。

## 調査と実装順序

1. 既存CI失敗をRedとして保持。ローカルで対象テストとUI併走時を比較し、画面状態・AX取得とMainActor待機を切り分ける。
2. 検証で判明した原因を資料へ反映し、必要な回帰テストを先行追加する。固定待機・ウィンドウ共有・転送の細粒度callbackを調査対象とし、未確認の原因は断定しない。
3. 根拠の得られた箇所だけ最小修正する。履歴位置維持、最新への復帰、SSEの逐次配信、2 MiB上限、取消・エラー伝播を維持する。
4. 関連テスト、通常の全非liveテスト、Lint、署名なし両CPU Releaseを実行。テスト除外・上限の一律延長・成功までの反復再実行は用いない。
5. 修正をコミット・pushし、GitHub CI成功を確認してPR #48をマージ。最新mainへ移動し、`feat/dr3-design-system` のみローカル・リモートから削除。

## 受入条件

- 履歴閲覧中の部分字幕更新で表示位置が奪われず、最新へ復帰できる。
- 長文・2 MiBちょうど/1 byte超過を実URLSessionと合成URLProtocolで検証。受信callbackの隔離、順序、取消、エラーの契約を維持。
- ローカルとGitHubのLint・非liveテスト・Release成功。実API・実音声は対象外。
- クリーンなmainで終了。調査・検証の事実と未検証事項を記録。

## 調査後の実装方針

- ローカル対象10定義・2suiteは4.327秒で成功。HTTP全体0.480秒、境界2ケース0.322秒。単独のHTTP処理遅延は再現しなかった。
- ウィンドウ/NSHostingViewを作る18suiteが並列実行され、個別の`.serialized`はsuiteをまたぐフォーカス・スクロール・AX状態を排他にしない。画面テストを共通の`AppKitIntegrationTests`親suiteへ配置し、その親を`.serialized`にする。ウィンドウを表示しない単体テストは従来どおり並列。
- 既存CIの失敗をRedとして、この実行構成だけを変更してローカル/リモートで比較する。テストの削除・タイムアウト変更・製品HTTPの変更は行わない。履歴AX失敗が残る場合はタイトルとviewportを診断に含め、別途原因を切り分ける。

## 残った履歴位置の調査

`0d2ccd7`のrun 43701249706ではHTTP全suiteが31.273秒で成功し、748定義中の失敗は履歴スクロール1件のみ。xcresultのcallStackで、失敗は字幕更新後の110行目からの`frame(of:in:)`呼出しと確認した。初期の字幕取得ではなく、更新前に見えていた字幕が更新後に取得できなくなっている。

CIはmacOS 26.7.2、ローカルは26.5.2。固定200ms後のAX取得は画面更新完了の条件を確認していない。字幕更新のレイアウト後、既存の`waitForTestCondition`で「更新前の同じ履歴行がviewportと交差する」を待つ。文字サイズ16/48pt、短文→長文→短文の連続更新も検証する。suiteの60秒上限と、既存条件待機の3秒上限は維持する。

位置制御の製品変更もローカルで試したが、行ID追跡や座標復元ではサイズ変更・48pt時の回帰が出たため採用していない。製品コードは元へ戻し、まずAX更新待機だけをリモートで検証する。失敗が続く場合は、タイムアウト時に記録した対象行名・画面内テキストから再調査する。

run 43703117723では条件待機後も16ptの履歴78行目が消え、17〜44行目が表示されていた。単なるAX更新遅延ではない。ScrollPositionとScrollViewReaderの併用をやめ、既存ScrollViewReaderだけで最新へ移動し、履歴閲覧中は移動要求を出さない構成を検証する。読み返し・連続更新・拡大文字・リサイズ後の末尾追従を全て維持する。

## 位置制御の修正候補と検証

ScrollViewReaderだけにするとリサイズ時の末尾追従が失敗したため採用しない。既存の末尾追従を保持し、履歴閲覧中の字幕更新でのみ`ScrollPosition()`へ置き換え、古い位置指定を解除する。履歴中は新しいスクロール先を指定せず、利用者の現在位置を保つ。関連9定義4suite（16/48pt・連続更新・リサイズを含む）が25.848秒で成功。全テスト・Release・リモートCIで最終確認する。

run 43703956190で位置指定解除のみでは解消しないことを確認。各行を`scrollTargetLayout`へ登録し、Stringの行IDをScrollPositionに伝える構成を追加検証する。更新前にも同じ行が可視のままであることを確認し、スクロール後処理だけでずれるかを区別する。移動方法全体を置き換える案は採用せず、既存の最新追従経路を維持する。

最終候補は既存コードへの`idType: String.self`と`.scrollTargetLayout()`の追加のみ。効果のなかった位置解除を撤回した。この構成で関連9定義4suiteが26.146秒で成功し、更新前の対照観測・連続更新後の履歴可視性・最新復帰・リサイズ後の末尾追従を同時に確認した。リモートCIでOS差を最終確認する。
