## 問題と確認範囲

目的は長い会議で途中字幕が頻繁に更新されても、確定済み履歴の整形・ソート・比較を毎回繰り返さないこと。認識結果や保存内容、表示順を変更しない。

| 経路 | 現状 |
|---|---|
| Conference原文 | `TranscriptPresentation.source`が全segmentsをfilter/map。補正ごとにunitsを先頭から検索し、結果へ途中字幕を追加 |
| Conference訳文 | 全unitsをmapし、各unitについて補正を検索。数件の文末待ちバッファを得るために全segmentsをfilter |
| Conferenceスクロール | `TranscriptPane.onChange(of: entries)`が原文・訳文の配列全体を比較 |
| Meeting主画面 | `transcriptEvents`は既に整列済みのfinalsと最大2件のpartialsを結合して再ソート。表示とonChangeで取得する |
| Meeting小窓 | 最大3行を表示するために全履歴のソート結果を作り、suffix(3)を取得 |
| Meeting訳文追従 | `onChange(of: translations.completed)`で訳文辞書全件から完了配列を作ってソート・比較 |

合成300／3,000／30,000発話で現行コードの整形処理を計測した。[変更前計測](../validation/r5-2-live-presentation-baseline.md)。これはSwiftUI描画や実音声遅延の測定ではない。

## 実装方針

### Conference：確定済み表示と途中字幕を分離

- 原文の確定行と訳文の確定単位の表示用配列を、途中字幕とは別に保持・再利用する。途中字幕だけが変わる場合、確定履歴のfilter/mapや補正対応表の再構築を行わない。
- 履歴の無効化を発話追加、翻訳単位追加、翻訳状態／本文変更、補正採用／取消、翻訳モデル準備状態、Clear／resetに接続する。原文と訳文で必要な更新を区別する。
- メモリ内の表示用状態と更新通知を用い、保存モデルへキャッシュやrevisionを追加しない。Viewのbody評価中にObservableな状態を書き換えて再描画を誘発しない。
- 文末待ちの原文は、既存の`segmentByID`によるバッファ参照を利用する。数件のバッファを得るための全segments走査を除く。
- `TranscriptPane`へ確定履歴と末尾の途中行を別々に渡し、途中更新時に全配列へappendしてコピーすることを避ける。行ID・表示文言・時刻・予約高を維持する。
- 補正で複数原文行を1行へまとめる現在の挙動、補正取消時の復元を維持する。補正や翻訳確定時の再計算は必要に応じて許容する。

### Meeting：整列済み履歴へ最大2件の途中発話を挿入して参照

- 表示専用の小さな`RandomAccessCollection`を用い、finalsをコピー・再ソートせず参照する。最大2件のpartialsだけを安定順で並べ、二分探索で挿入位置を求める。
- 同時刻では現在と同様に確定発話を先にし、確定発話どうしの順序と途中発話どうしの現在の配列順を維持する。確定前後のIDは維持する。
- 主画面と小窓の両方で同じ表示コレクションを利用する。小窓は末尾3件だけを読み出す。全履歴をArrayへ変換する呼び出しを残さない。
- `MeetingSessionStore.finals`の保存用配列や受信時の重複排除・確定順序・onFinalの契約を変えない。

### スクロール追従：全文比較を更新通知へ置き換える

- `.onChange(of: entries/events)`を、受理した発話更新・途中結果消去・resetを表す小さな更新通知へ置き換える。拒否した古いrevisionや別セッションのイベントで通知を進めない。
- Meetingの`translations.completed`は保存・書出し用として残し、ライブ表示の追従判定では完了配列を作らない。翻訳の表示に関係する状態変更とresetを通知する。
- 最新追従中だけ下端へ移動し、履歴閲覧中は翻訳・途中字幕の到着で位置を奪わない。根拠ジャンプ、同じ根拠への再ジャンプ、「最新へ」、文字サイズ・幅変更を維持する。

名称・内部の分割は実装時に最小構成へ調整する。汎用キャッシュ基盤や共通通知フレームワークは作らない。使われなくなった全件整形経路・配列比較・テスト専用の旧APIは整理する。

## 手順と受入条件

1. **資料を更新する。** [字幕表示設計](transcription-mode.md)とplan.mdへ承認された変更を反映。R5-1の未コミット変更を保持する。
2. **TDDのRed。** `tdd`に従い、表示順と無効化条件、途中更新だけでは確定履歴を再生成しない条件を先行テストにする。旧実装での失敗を確認する。
3. **最小実装。** Conferenceの分離、Meetingの表示コレクション、スクロール通知を順に変更し、各段階で関連テストを通す。
4. **同じ入力で計測。** 合成300／3,000／30,000件＋200途中更新を使い、修正前後で表示内容と必要な変更検知が一致することを確認する。表示用データ準備とSwiftUI描画の負荷を区別する。
5. **最終検証。** 全liveフラグ0で全テスト、SwiftLint strict/no-cache、Releaseビルド、差分確認。記録は`docs/validation/r5-2-live-presentation.md`へ保存。

| 受入対象 | 期待結果 |
|---|---|
| Conferenceの途中更新 | 確定原文・訳文の再生成0回。途中行の本文／予約高だけ更新。全segmentsからのバッファ検索0回 |
| Conferenceの確定・翻訳 | 新規確定、バッファflush、準備中／失敗／再試行、訳文完了が表示へ反映 |
| 補正 | 複数segmentの採用・取消で既存と同じ行／文言／IDへ変化。途中更新でも採用状態を保持 |
| Meetingの順序 | 0／1／2途中入力、途中発話が確定発話より前にある場合、同時刻、確定化、clearPartials、resetで現在の順序・ID・本文と一致 |
| Meetingのコスト | 途中更新ごとの全finalsソートと全配列生成0回。小窓は末尾3件の取得に全件を列挙しない |

SwiftUI自身の差分評価・レイアウトが全履歴に対して常に定数時間になるという保証はしない。まずアプリが毎回行う全件整形・ソート・比較を除く。キャッシュ分の保持メモリは合成大規模ケースで確認する。

## 対象外・承認

認識エンジン・翻訳アルゴリズム・字幕の内容・履歴上限・保存形式・R5-1の要約上限は変更しない。R5の検索語選択とR6、実音声・実API評価・配布・コミット・PR作成は今回の対象外。

本計画のローカル実装・検証は2026-11-14のユーザー「進めて」で承認済み。ユーザー指定AGENTS.mdの「実装前に実装計画を…作成し承認を得る」に基づく確認。調査・計測・計画作成後の「進めて」で承認を得て、資料更新・TDD・実装・検証を実施した。

## 実施結果（2026-11-14）

- Conferenceは`SessionStore`内の非Observableキャッシュと`TranscriptEntries`、Meetingは`MeetingTranscriptTimeline`と表示revisionで実装した。主画面・小窓の全履歴再ソートと追従時の全配列比較を除いた。
- TDDで旧処理の履歴再生成・30,000件列挙を検出。全629テスト中622成功・実API7skip、Lint243ファイル違反0、Release成功。
- 合成UIで閲覧行の可視性、根拠ジャンプ、「最新へ」、リサイズ後の下端追従を確認。厳密な座標固定テストは旧表示処理でも失敗したため、ピクセル単位の位置固定は保証せず、既存の遅延レイアウト由来の変動として記録した。
- 30,000件・200途中更新のデータ準備はConference補正なし1,385.941→0.275ms、Meeting229.730→0.334ms。全表示内容の同値性を確認。描画時間・長時間実機耐久は未測定。
- キャッシュ保持によるRSS増は合成30,000件で約7.9MB。1,000途中更新で増加せず、reset後の履歴オブジェクト解放を確認。独立レビューは未実施。
