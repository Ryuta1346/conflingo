## 調査結果

- `SavedSession` / `SessionSnapshot` と `SavedKnowledge` / `KnowledgeArchive` は、ドメイン型を含めて合成Codableに依存している。`SessionSnapshot` と `TranslationState` は関連値を持つenumで、case名・関連値の構造も保存形式に影響する。
- `SessionFiles` と `KnowledgeLibraryFiles` はversion 1を読み込み、参照整合性などを検証する。JSONEncoder / JSONDecoderの既定の日付表現を使用している。
- 既存の永続化テストは、その時点のコードによる保存→再読込が中心。同時に変わったencoder / decoderだけでは、以前のv1データが読めなくなる変更を検出できない。
- Meetingの`translations` / `assistance`、Conferenceの`support`や発話の入力情報などは任意項目。これらがないデータの読込も固定する。
- テストターゲットには現在Resourcesビルドフェーズがない。fixtureをテストバンドルへ格納する設定を追加し、ソースの絶対パスに依存せず読む。

製品コードは既存契約への回帰が見つかった場合だけ最小修正する。新たな保存DTO、移行機構、形式バージョン、ユーザーデータの書換えは追加しない。

## fixtureと確認対象

1. **Meetingの基本v1:** 翻訳・共通支援の任意項目がない形式。マイク／内部音声の確定発話、候補の確認状態、要約、資料引用を保持する。
2. **Meetingの拡張v1:** 入力別の訳文、共通支援、Web出典・検索候補HTML、リポジトリ由来の引用を保持する。保存可能な候補種別・確認状態を網羅する。
3. **Conferenceの基本v1:** supportと後付けの発話属性がない形式。`pending` / `translating` / `done` / `failed(String)`、訳文の有無を保持する。
4. **Conferenceの拡張v1:** 入力元・発話時刻・言語、資料質問、採用済み補正と元の原文／訳文、適用用語を保持する。
5. **通常資料のv1:** 本文、文字数、取込日時、ID・revision、sourceなしを保持する。
6. **リポジトリ資料のv1:** 複数ファイルの相対パス・本文・ハッシュ・snapshot IDを保持する。

fixtureは基点の形式から作る合成データであり、実ユーザーの保存ファイルや過去リリースから採取した証跡とは記載しない。任意項目なしの形は履歴と照合して由来を記録する。

## 実装・検証手順

1. **資料を確定:** この計画の承認後、v1の固定範囲とfixture更新規則をREADMEへ記載する。plan.mdのR3をDOINGへ進める。
2. **テストを先行:** 固定JSONを入力として、公開のファイル読込経路での復元と期待値を検証する。fixtureをテスト実行中に現在のencoderから生成しない。
3. **検出力を確認:** 既存互換性のテストは基点で成功し得る。テスト資源の未配置による失敗を互換性のRedとは扱わず、別の一時作業コピーでフィールド名／enum caseの破壊的変更を入れ、対象テストが期待する理由で失敗することを記録する。変更は本成果物へ残さない。
4. **最小実装:** リソース読込と必要なテスト補助だけを追加する。不具合が判明した場合は、先行した失敗テストを通す最小修正を行う。
5. **保存契約を両方向で検証:** 読込後のモデルを再encodeし、固定JSONと構造比較する。オブジェクトのキー順・空白・エスケープ表記は比較対象外、キー名・enumの形・配列順・数値・本文は比較する。任意項目の消失を見逃さないよう、主要値は固定した期待値でも確認する。
6. **利用経路を検証:** fixtureを一時ディレクトリに配置して一覧・読込を確認。SessionsはMarkdownに原文・訳文・引用が残ること、資料は復元後に検索・引用できることを確認する。保存経路の出力も固定JSONの契約と比較する。保存時に生成されるID・revision・更新日時のみ、返された値を使って明示的に扱う。
7. **最終確認:** 関連テスト→全テスト（実API評価無効）→`swiftlint lint --strict --no-cache`→Releaseビルド。fixtureがテストバンドルに存在し、製品アプリに入らないことも確認。結果と未確認事項を記録する。

既存の破損・未来version・不正参照・書込失敗・パス安全性のテストは維持し、同じ検証を重複追加しない。音声取得・追加実APIは不要。

## 受入条件

- 6種類の固定v1 JSONが製品の読込・検証経路を通り、主要な本文・参照・翻訳・状態・日時が期待どおり復元される。
- 現在のencoder / decoderが同時に変わっても、既存v1と非互換なフィールド名・enum構造の変更をテストが検出する。
- JSONの意味が変わらないキー順・整形の差でテストが失敗しない。
- 任意項目がない基本形式の読込と、存在する拡張項目の保持をどちらも確認する。
- fixtureの自動上書き機能を設けない。互換性を壊す変更への対処として既存fixtureを更新せず、変更理由・バージョン方針を別途検討する。
- 全テスト・Lint・Releaseが成功し、R3の検証証跡を残す。PRマージまではR3をDONEにしない。
