## 確認した問題

- SSE受信層と2種類のストリームデコーダーが、イベント情報を含めて262,144 bytesで拒否する。
- ストリームには別途、1行・1イベント・復号したJSON本文に65,536 bytes、表示本文と補足それぞれに8,000文字の制限がある。
- Web調査の受信層とJSONデコーダーも全応答262,144 bytes。本文8,000文字、出典20件、検索候補HTML65,536 bytesなどは別に検証する。
- 実ソースを使用した合成計測で、同じ8,000文字の本文を1文字ずつのイベントにすると上限超過になることを確認した。[測定結果](../validation/r2-response-size-investigation.md)。Geminiの実測は[数値記録](../validation/r2-response-size-live-2026-11-13.json)を参照。他社は未測定。

## 手順

1. **調査（完了）:** 上限の適用箇所を洗い出し、同じ本文でイベント分割だけを変えるローカル計測を行う。実APIの評価条件を[ヒアリングシート](r2-response-limit-hearing.md)へ記載する。
2. **実測（4/4要求完了）:** まず既存Geminiモデルで日英の要約とWeb調査を計4要求。本文・秘密情報を保存せず、受信量、本文量、最大行・イベントサイズ、イベント数、usage、終了理由を記録する。ほかのプロバイダーは対象モデルと追加枠を確定してから評価する。
3. **修正方針の確定:** 表示本文・復号済みJSONと通信上の付加情報を分ける。測定に基づく有限の受信上限を残し、本文が短ければ無制限に受信する設計にはしない。通信層・デコーダーの制限を同時に整合させる。通信全体の上限を2 MiBとし、既存の復号JSON65,536 bytes、SSE行/イベント65,536 bytes、表示本文8,000文字は維持する。
4. **TDDで修正:** 長い正常応答が完了する回帰テストを先行し、意図した失敗を確認する。行・イベント・本文・総受信量の境界と1 byte超過、UTF-8分割、検索メタデータ、取消・期限切れ・不正終端を検証する。URLProtocolを使い実際の受信層とデコーダーの結合も確認する。
5. **最終検証:** 関連・全テスト（live評価無効）、SwiftLint strict/no-cache、Releaseビルド、自己レビューを実施。実APIの測定結果と合成試験を区別して記録する。

## 受入条件

- 既存の意味上の本文上限内で、SSE分割や検索結果の付加情報が旧受信上限を超えても、定めた新しい受信予算内では正常に完了する。
- 応答の巨大化・無期限受信は有限の上限と期限で停止する。取消、不正応答、終端・引用の検証を維持する。
- 要約・質問・Web調査の全利用箇所で制限が一致する。
- 各社の実測済み／未測定を明示する。今回の合成試験だけでR2をDONEにしない。
- コミット・push・PR作成・アプリ更新は別指示まで行わない。


## 実測後の修正判断

Gemini4要求では超過は未再現だが、7経路の合成長文は約46〜73万bytesとなり、従来の262,144 bytesで拒否された。本文・JSONの許容サイズを増やす必要はなく、SSEの付加情報とWeb検索結果を収容する通信上の予算を分ける。

- `LLMResponseLimits`に総受信2 MiB、SSE行/イベント64 KiB、復号JSON64 KiBを名前付きで定義する。総受信値はネットワーク層2か所とデコーダー3か所へ同時適用する。
- 2 MiBは製品上の有限の保護上限。本文8,000文字＋補足8,000文字を1文字ごとに分割した合成SSE（各経路とも2 MiB未満）を収容しつつ、全JSONを保持するWeb調査のメモリ増加を8倍に限定する。各社の全応答を保証する実測上限ではない。他社・大規模検索は未受入として残す。
- 当初候補の8 MiBは、Debugで複数の巨大応答を同時受信する境界試験が製品の60秒期限にも到達した。試験時間だけの延長では解決せず、製品の期限を維持して、確認済みの合成ケースを収容する2 MiBへ縮小した。最大JSON64 KiBを任意に細分化した全応答を受理する保証は設けず、通信予算を独立した制約として残す。
- Web調査は全JSONをメモリで保持するため最大2 MiBまで増える。無制限受信は許可しない。文字数・引用・検索候補HTMLの既存制限と通信期限は変更しない。
- 追加回帰は新しい総受信上限のちょうど境界/1 byte超過、復号JSON境界、本文上限、UTF-8分断、SSE長文、通信層からの復号、デコーダーエラーでの受信停止。実APIは4/4要求を消費済みで再実行しない。
