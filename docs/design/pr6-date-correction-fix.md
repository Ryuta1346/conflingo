## 修正する契約

Q05を次の優先順にする。

1. 同一対象の日程が明示的に訂正・変更された場合、発話で報告された変更として新しい日付を説明する。どちらが正しいかを再質問せず、独自に合意済みと認定しない。
2. 変更の提案・質問だけの場合、新しい日付を採用済みにしない。提案であることを保持する。
3. 同一対象について異なる日付が示され、訂正・変更で解消されていない場合だけ、食い違いを説明して正しい日付を確認する。
4. 対象が不明な発話では予定変更か曜日の説明かを断定せず確認する。

## 変更と検証

- `GeminiInsightClient`の日程指示を整理する。モデル・推論設定・スキーマ・UI・後処理は変更しない。
- 既存24ケースを維持し、日英の変更済み・変更案4ケースを追加する。変更済みは`answerSuggestion`、変更案は`decisionCandidate`または`answerSuggestion`を許容し、本文の意味を別に判定する。
- 本体修正前に追加ケースと既存の日程4ケースを実モデルで評価する（最大8要求）。旧版で失敗を観測できなければRedと称さず、指示の欠陥と観測結果を区別する。
- 修正後は全28ケースを1回評価する。明示変更の保持、提案の未確定扱い、未解決矛盾、曖昧さ、およびQ01〜Q06を目視確認する。自動判定は構造・根拠ID・種別に限定し、意味を保証するキーワード検査やプロンプト全文一致テストを追加しない。
- 既存の一時ランナーと登録済みキーを用い、合成テキストだけを送る。キーはメモリ経由、回答は目視だけとし、記録は判定理由・使用量・ソースハッシュに限定する。最大36要求、再送なし。失敗時は記録し、無変更の反復を行わない。
- 全ローカルテスト（実APIテスト除外）、Releaseビルド、SwiftLint、差分検査を行う。既存の23/24記録は旧版の証跡として保存し、今回の検証を別に記録する。

Q05の既知の失敗も再評価するが、単回評価を一般的な品質保証やPR6全体の受入完了とはしない。コミット・pushは本作業に含めない。

## 1回目評価を受けた調整

修正前8件では明示変更の誤動作は再現せず、既知の`ja-explicit-conflict`の失敗を確認した。修正後28件では変更済み・提案・明示矛盾が合格した一方、`ja-conflict`が矛盾を断定する回帰を観測した。曖昧な対象の検査が日程分類より後に置かれていたため、対象の特定を先に行う指示へ変更する。今回の修正指示の範囲で全28件を追加評価する（累計上限64要求）。無変更の再送は行わず、1回目の結果も保存する。

2回目も`ja-conflict`で「矛盾なし」の断定を観測。対象確認の順序だけでは不十分だったため、曖昧な発話と同一対象が明示された発話の回答例を対にして追加する。例文の日付と対象は評価ケースと変え、既存の評価ケースは変更しない。全28件を追加評価（累計上限92要求）し、過去2版の失敗も残す。
