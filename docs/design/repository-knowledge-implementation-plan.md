## 目的と範囲

ローカルにあるプロダクトの実装・テスト・設計文書を会議の参照資料として選択し、手動質問と終了後の要約に使う。回答から取り込み時点のファイルと行番号を確認できるようにする。

- Preparationでフォルダ選択→対象確認→取り込み。Liveで手動質問と引用閲覧。Reviewで資料付き要約とMarkdown出力。
- 既存Markdown/Textも同じ資料付き要約に利用可能とする。
- 会議中の自動提案への資料付加、GitHub接続、clone/pull、リポジトリ変更、コード実行、常駐監視、永続ライブラリは今回含めない。
- 資料は会議内のみ保持し、会議破棄・アプリ終了で消える。取り込み元は変更しない。
- 実装・ローカル検証を本計画の対象とする。実API品質評価と実音声結合は別の送信範囲・要求数・予算を確認して実施し、fakeの成功で完了扱いにしない。

| 現行 | 今回の変更 |

## 取り込みの契約

### 選択・対象・上限

- OSのフォルダ選択で明示的に選んだルート内を読む。App Sandboxを維持し、security-scoped accessは読み込み中だけ使用する。外部プロセスやGitコマンドには依存しない。
- 初版は会議あたり1リポジトリ。準備画面で取り外して別フォルダを選べる。Git管理の有無にかかわらず、ユーザーが選んだ作業フォルダのスナップショットとして扱う。
- 初期対応: `.swift/.m/.mm/.h/.c/.cc/.cpp/.hpp/.rs/.go/.java/.kt/.kts/.py/.rb/.php/.js/.jsx/.ts/.tsx/.vue/.svelte/.html/.css/.scss/.sql/.sh/.md/.txt/.json/.yaml/.yml/.toml/.xml/.plist`、`Dockerfile/Makefile/Package.swift`。UTF-8の通常ファイルのみ。言語ごとの構文解析や全言語対応を約束しない。
- 初期上限案: 選択ファイル1,000件、1件1 MiBかつ10万文字、リポジトリ合計500万文字・入力20 MiB。通常資料は従来の20件・50万文字を維持。走査は最大20,000エントリ・深さ32まで。上限に達した場合は部分的に完了したように扱わず、対象の絞り込みを求める。
- `.git`、隠しファイル/ディレクトリ、依存パッケージ・ビルド生成物（`node_modules/vendor/.build/build/dist/DerivedData/Pods/Carthage`等）、lockfile、minifiedファイル、バイナリを除外する。`.env*`、秘密鍵・証明書・認証情報の既知ファイル名を除外する。通常ソース内の秘密情報を完全検出できるとは表示しない。
- `.gitignore`の完全な評価は初版では行わない。固定除外規則と対象一覧の確認を適用し、「Git追跡ファイルだけ」とは表示しない。
- シンボリックリンク、ディレクトリリンク、サブモジュール/入れ子のGitルートは対象外。選択ルート外への解決を拒否し、列挙時だけでなく開く時にもファイル種別と境界を検証する。
- 取り込み前に相対パス・形式・サイズ・除外理由を表示し、ファイル/ディレクトリ単位で対象を外せる。全選択数と上限を表示する。選択した対象が読めない場合は失敗理由を示し、未読のまま成功扱いしない。

### 版・位置・ライフサイクル

- 「取り込み時点の作業ツリー」と明示。リポジトリ表示名、相対パス、取り込み時刻、ファイル内容ハッシュとスナップショットIDを保持する。
- HEAD・コミットとの一致や未コミット変更の有無は推測しない。初版の版識別は内容ハッシュを使い、特定コミットの内容としては表示しない。複数ファイルが単一時刻のGit状態である保証も行わない。
- 各ファイルの読み込み前後のサイズ・更新情報を比較し、観測できた途中変更は取り込み失敗として再試行を案内する。以後の検索・送信・引用は読み込んだ不変本文だけを利用する。
- 同じ本文が複数パスにある場合も出典を統合しない。重複判定は同一スナップショット内の相対パスを基準とする。
- 一括取り込みは取消可能。検索索引の構築が成功してからまとめて公開し、途中失敗・取消では既存資料を維持する。UI/音声処理をブロックしない。
- 元の絶対パスやGit remote URLはAPI・ログ・Markdownへ出さない。リポジトリ名と相対パスは引用情報として送信・出力対象になることを示す。
- 取り外しで新規検索・送信を止める。生成済みの引用スナップショットは従来どおり会議破棄まで保持する。

## 検索と手動質問

- 既存FTS5を利用する。相対パス・ファイル名・camelCase/snake_case等の識別子分割と原語、コメント・本文を検索語へ追加する。パスや識別子を優先する順位を固定fixtureで検証する。
- 引用は原文へ戻し、相対パス・開始/終了行・文字位置・版識別を保持する。1チャンク最大1,200文字を維持し、長い行・Unicode・改行正規化も欠落なく扱う。
- 手動質問は既存の最大5箇所・6,000文字と二重許可を維持する。相対パス等のメタデータは本文とは別に上限を設け、HTTP全体の制限も維持する。長いパスを切り詰めて別ファイルと混同しない。
- 日本語の機能質問から英語コードを検索するケースを評価する。共通語、識別子、文書・コメントから辿れない場合は一致なしを示し、リポジトリ全体を理解したと称さない。初版はEmbeddingやLLMによる検索クエリ生成を追加しない。
- 設計文書、テスト、実装の出典を区別する。コードに処理が存在することと、本番で有効・検証済みであることを混同しない。

## 終了後要約

### 確認画面と送信

- 既存の「発話のみ」に加え「資料も参照」を要約確認画面で選べる。初期値は発話のみ。今回の要約への同意として扱い、会議中の手動質問の資料許可を自動的に再利用・変更しない。
- 資料付きの場合、既存の最大20区間に分割した各区間の発話からローカル検索する。全発話を検索に用い、先頭2,000文字だけで後半を落とさない。発話ごとの検索結果を重複排除し、順位集計で区間あたり最大5箇所・6,000文字へ収める。追加のAI検索要求は行わない。
- 生成前に各区間のファイル・抜粋・文字量と生成要求数を確認できる。最大の追加資料本文量は20区間×6,000文字。一致なしの区間はその旨を表示して発話のみで生成する。検索失敗は一致なしに置き換えず、確認画面へ戻す。
- 確認から生成まで発話、資料の版、選択、回答言語を固定する。変更・取り外し・破棄で確認済みplanを無効化し、再確認なしの送信をしない。
- 1区間1生成、直列実行、区間ごと60秒、既存の発話上限・全区間失敗時停止・完成済み要約保持を維持する。API利用料が発生する旨と資料抜粋がGeminiへ送られる旨を表示する。

### 要約の意味と引用

- 各区間で「会議の要約」と「資料・実装からの補足」を分けて表示する。資料を使わない場合は既存の要約表示を維持する。
- 会議の要約には当該区間の発話根拠を必須にする。資料だけを根拠に会議での合意、担当、期限、発言を追加しない。
- 資料補足は専用の構造化フィールドと資料引用を持たせる。補足が空なら表示しない。補足があるのに有効な資料引用がない場合や、送信していない引用IDが返った場合は応答を不正として扱う。
- 発話とコード/文書が食い違う場合は両者を区別し、勝手に訂正・合意済み扱いしない。候補の確認状態をAIは変更しない。
- 資料付き要約専用の応答契約を追加し、手動回答・自動提案・発話のみ要約の応答契約は維持する。資料内の命令・コメントは根拠データとしてのみ扱う。
- Reviewで発話と資料の引用を開ける。Markdownにも補足・相対パス・行・版・抜粋を残し、ファイル名やコード内の記号で出力構造を変えない。

### 取消

- AI停止、要約取消、Keychain変更、会議破棄、参照資料の取り外し/変更で待機中・処理中のplanと要求を無効化する。後続区間を送らず、遅延応答を採用しない。
- 取り込み/検索/要約の取消を既存の手動質問の無効化と両立させる。`onChange`を上書きして既存取消を失わせない。
- 資料付き生成が失敗しても、以前の完成版を保持する。部分生成は完成版として保存・表示しない。送信済みデータを取り消せるとは表示しない。

## 受入条件

| ID | 確認する振る舞い |
|---|---|
| K01 | 除外規則、ルート外/リンク拒否、非UTF-8、上限、途中変更、取消/失敗で既存資料を保持 |
| K02 | 同名別パス・同本文別パスを区別し、原本変更後も取り込んだ本文・行・版を引用 |
| K03 | Swift/TypeScript等の代表fixtureで識別子・パス・コメント・日本語機能質問を検索。期待する根拠が上位5件に入るケースと検索不能ケースを明示 |
| K04 | 手動質問は許可時のみ最大5箇所/6,000文字。自動提案の資料送信は0 |
| K05 | 資料付き要約は全発話から区間検索し、確認したスナップショットと要求数・内容が一致。未同意時は送信0 |
| K06 | 未送信の引用ID・発話根拠なし・引用なしの資料補足を拒否。候補を自動確定しない |
| K07 | 資料取り外し・キー変更・停止・破棄・遅延応答の競合で後続送信0。既存の手動回答取消も維持 |
| K08 | 発話のみ要約の内容・30/60秒の期限・区間数・旧完成版保持・Markdownの既存動作を維持 |
| K09 | Review/Markdownで会議要約と資料補足を区別し、コード/文書の矛盾、ファイル名注入、相対パスと行位置を確認 |
| K10 | 非録音UIでフォルダ追加→検索→手動引用→終了後要約の確認→取消/完了→引用→出力。狭幅・キーボード・失敗状態を確認 |

自動テストは合成ファイルとfake client/transportを使い、利用者の実リポジトリを外部送信しない。合成の日英品質ケースには「文書では予定・コードでは未実装」「実装はあるが会議では採用未決定」「テストの期待とコードの差」「コード中の命令」「一致資料なし」を用意する。実モデルの意味的品質は後続の実API評価まで未確認とする。

検証: 全live評価フラグを無効にした `xcodebuild test -project ConfLingo.xcodeproj -scheme ConfLingo -destination 'platform=macOS'`、Debug/Releaseビルド、`swiftlint lint --strict --no-cache`、`git diff --check`。実施時にテスト数・ログ・未検証事項を記録する。
